# Discord ↔ Telegram Bridge

Настраиваемый двусторонний мост для пересылки сообщений между Discord-каналами и Telegram-группами. Маршрутизация использует **числовые ID** чатов.

В Discord сообщения Telegram выглядят так: профиль webhook **«Имя автора · Telegram»**, под ним текст сообщения. Остаётся системная отметка приложения; это сообщение интеграции. Можно указать публичный аватар отдельно для каждого Telegram ID. В Telegram используется общий профиль бота и подпись в теле сообщения на двух строках: `[Discord] Имя:` и затем текст. Для сообщений только с медиа подпись автора добавляется к медиа. Telegram Bot API не предоставляет имя/аватар отправителя отдельно для каждого исходящего сообщения.

## Что реализовано

- Текст в обе стороны; изображения и видео отправляются с предпросмотром, GIF — как анимация, обычные файлы — документами. Если целевая платформа не принимает предпросмотр, сохраняем файл документом; при невозможности передачи оставляем исходный текст и точное уведомление о лимите или отказе.
- Ответы по сохранённым ID; для Discord webhook — читаемая цитата. Известные ответы в Telegram оформляются обычным reply. Если мост не знает оригинал, используется цитата или сообщение о недоступности оригинала.
- Редактирование текста и состава вложений в обе стороны. Удаление Discord → Telegram для известных оригиналов, включая bulk delete. Удаление Telegram → Discord отсутствует: Bot API не присылает события удаления обычных групповых сообщений.
- Несколько независимых пар через `[[pairs]]`, при необходимости отдельные темы Telegram и существующие Discord threads. Для вашего сценария достаточно одной пары.
- SQLite inbox/outbox, сохранение ID, защита от повторных событий и от зацикливания. Отдельные checkpoint для каждой отправленной части. После перезапуска отправленные части повторно не создаются.
- Ограниченные повторы временных ошибок, экспоненциальная задержка, учёт `retry_after`, pacing запросов. Спорные отправки сохраняются для проверки оператором.
- Фильтры чатов, служебных событий, команд `/` и `!`, других ботов. Собственные сообщения и Discord webhooks не пересылаются независимо от настройки `ignore_bots`.
- Запуск на Windows с защищённым вводом секретов и необязательным автоперезапуском. Скрипты не устанавливают задачи Windows и не запускают фоновые процессы сами.

## Архитектура и структура

Исходная рабочая папка была пустой, Git-репозитория и пользовательского кода не было. Выбран Python 3.11+ и один процесс `asyncio`, SQLite из стандартной библиотеки, `discord.py 2.7.1`, `python-telegram-bot 22.8`, `aiohttp 3.14.5`. Это поддерживаемые **сторонние** Python-библиотеки для официальных API, а не официальные SDK платформ.

`discord.py` получает Gateway-события и выполняет идемпотентные изменения сообщений. Отправка в Discord использует официальный REST API v10 напрямую: это позволяет избежать скрытых повторов POST и включить `enforce_nonce` в режиме обычного Discord-бота. В webhook-режиме Discord не предоставляет этот параметр. Telegram использует Bot API через библиотеку и long polling; публичный сервер/webhook для получения Telegram-событий не нужен.

```text
bridge/config.py       проверка конфигурации и секретов из окружения
bridge/ingest.py       фильтры и нормализация платформенных событий
bridge/store.py        SQLite: события, операции, соответствия сообщений
bridge/engine.py       доставка, ответы, изменения и повторы
bridge/transports.py   API, вложения, лимиты и pacing
bridge/runtime.py      подключения, проверка доступа, обработчики, health
bridge/discovery.py    получение Telegram ID локальной командой
scripts/start.ps1      запуск и перезапуск на Windows
scripts/check.ps1      lint, тесты и сборка
tests/                 локальные тесты с моками API
```

Для каждого направления пары работают два обработчика. Медленная загрузка не занимает обработчик приёма событий и не останавливает соседние сообщения. Изменения одного исходного сообщения обрабатываются последовательно. Разные сообщения могут доставляться в несколько ином порядке; это сознательный компромисс в пользу независимой обработки. База рассчитана на один процесс на локальном диске; файловая блокировка защищает от повторного запуска с той же базой. Внешние брокеры и Docker для выбранного Windows-сценария не требуются.

## 1. Подготовка Python

Откройте PowerShell в папке проекта. Нужен установленный Python 3.11 или новее.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e .
Copy-Item -LiteralPath config.example.toml -Destination config.toml
```

Если `config.toml` уже существует, редактируйте его, не копируйте пример поверх. В текущей рабочей папке виртуальное окружение и зависимости уже подготовлены. Активация окружения не обязательна.

## 2. Создание Discord-приложения с нуля

1. Откройте [Discord Developer Portal](https://discord.com/developers/applications), создайте приложение **New Application** и его бота в разделе **Bot**. Выберите общий профиль моста.
2. В **Bot → Privileged Gateway Intents** включите **Message Content Intent**. Без него бот не получит обычный текст и вложения. **Server Members** и **Presence** этому мосту не нужны. Для крупных/верифицированных приложений Discord может требовать согласование Message Content.
3. Сохраните Bot Token локально: при запуске скрипт запросит его скрытым вводом. Не вставляйте его в код, конфигурацию, URL браузера или чат.
4. В **OAuth2 → URL Generator** выберите scope **bot**. Добавьте бота на нужный сервер. Scope `applications.commands` не требуется: управляющих команд в чатах нет.
5. Дайте в настроенном Discord-канале только **View Channel**, **Read Message History**, **Send Messages**, **Attach Files**. Для Discord thread дополнительно нужно **Send Messages in Threads** и доступ к ветке. Права **Administrator**, **Manage Messages** и **Manage Webhooks** самому боту не нужны. Убедитесь, что запреты на уровне канала не перекрывают разрешения роли.
6. В пользовательских настройках Discord включите **Advanced → Developer Mode**. Правой кнопкой по каналу → **Copy Channel ID**. Запишите его в `discord_channel_id` файла `config.toml`.
7. Для выбранного оформления откройте настройки **этого канала → Integrations → Webhooks**, создайте Incoming Webhook, задайте общий аватар по умолчанию и скопируйте URL. Создающему человеку нужно право **Manage Webhooks**. URL является секретом; скрипт запросит его как `DISCORD_WEBHOOK_COMMUNITY`.

При запуске мост проверит, что webhook действительно принадлежит указанному каналу. Если нужен режим общего Discord-бота без персональных имён, уберите `discord_webhook_env` из пары.

## 3. Создание Telegram-бота и получение ID группы

1. Откройте проверенного [@BotFather](https://t.me/BotFather), выполните `/newbot`, задайте имя и username бота. Сохраните выданный токен локально. Через настройки BotFather можно поставить общий аватар моста.
2. В BotFather выполните `/setprivacy`, выберите бота и **Disable**. После изменения удалите бота из группы и добавьте заново. Это нужно для получения всех обычных сообщений. Делать бота администратором вместо отключения privacy не обязательно.
3. Добавьте бота в настроенную Telegram-группу. Разрешите отправлять текст, фото, видео и документы. Администраторские права для обычной работы и удаления собственных исходящих сообщений не нужны.
4. Пока мост ещё **не запущен**, задайте токен в текущей PowerShell-сессии скрытым вводом:

```powershell
$secret = Read-Host 'TELEGRAM_TOKEN' -AsSecureString
$env:TELEGRAM_TOKEN = [System.Net.NetworkCredential]::new('', $secret).Password
$secret.Dispose()
```

5. Отправьте в группе `/bridge_id` (боту не нужно отвечать), затем выполните:

```powershell
.\.venv\Scripts\python.exe -m bridge telegram-chats
```

Команда выведет локально JSON с названием группы, `telegram_chat_id` и при наличии `telegram_thread_id`. Она не пересылает сообщения, не печатает токен и не подтверждает/сбрасывает pending updates. Числовой ID группы отрицательный, у супергрупп обычно начинается с `-100`. Впишите **полный** ID в `config.toml`. Если список пуст, отправьте `/bridge_id` ещё раз и повторите. Не запускайте эту команду одновременно с мостом или другим polling-процессом этого бота.

В обычной группе оставьте `telegram_thread_id` закомментированным. В форуме нужно явно выбрать тему и указать её ID: сообщения других тем игнорируются. Полученные до запуска группы/служебные updates будут отфильтрованы, команда `/bridge_id` не будет переслана.

## 4. Конфигурация и аватары

В `config.toml` замените демонстрационные ID на реальные. Токены туда не добавляйте. Параметр `name = "community"` — внутреннее стабильное имя пары; названия групп не используются для выбора маршрута.

Секреты передаются только окружением:

| Переменная | Где взять |
| --- | --- |
| `DISCORD_TOKEN` | Developer Portal → Bot → Token |
| `TELEGRAM_TOKEN` | @BotFather после `/newbot` |
| `DISCORD_WEBHOOK_COMMUNITY` | Настройки нужного Discord-канала → Integrations → Webhooks |

Если переменные отсутствуют, Windows-скрипт запросит их скрытым вводом. Они сохраняются в памяти текущего процесса PowerShell и наследуются дочерним Python, а не записываются скриптом на диск. При новом запуске PowerShell их нужно ввести заново. При уже заданных переменных повторного запроса нет. Для полностью неинтерактивного запуска предусмотрен `-NonInteractive`; в таком случае секреты должен предоставить ваш менеджер секретов/окружение заранее.

Для персональных аватаров Telegram-пользователей в Discord добавьте в конец `config.toml`:

```toml
[avatars]
"123456789" = "https://example.com/public-avatar.jpg"
```

Это демонстрационный пользователь и URL. Нужны реальные Telegram user ID и публичные HTTPS-ссылки на картинки, выбранные для этих пользователей. Автоматического скачивания/публикации аватаров нет. При отсутствии ссылки используется общий аватар webhook. **Нельзя** использовать URL вида `api.telegram.org/file/bot...`: он раскрывает токен. Такие ссылки, query-параметры и пароли в URL конфигурация отвергает. Изменение профиля автора уже опубликованного webhook-сообщения не синхронизируется задним числом.

Несколько пар добавляются повторением `[[pairs]]`. Для каждой используйте свой Discord channel ID, уникальную Telegram-группу/тему и при необходимости отдельное имя переменной webhook. Повторные конечные точки отклоняются. Мост отказывается запускаться с существующей базой, если конечные точки или режим webhook уже сохранённой пары изменились: для сознательного переноса нужна отдельная база, чтобы очередь не ушла случайно в другой чат.

## 5. Запуск на Windows

После заполнения ID:

```powershell
.\scripts\start.ps1 -RestartOnFailure
```

Если локальная политика PowerShell запрещает скрипты, запустите для этого процесса:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\start.ps1 -RestartOnFailure
```

Скрипт запросит недостающие секреты, проверит локальную конфигурацию и запустит мост. При временном сбое процесса выполнит до 10 перезапусков с растущей задержкой 2–60 секунд. Ошибки конфигурации (код 2) и штатная остановка не повторяются. `-MaxRestarts` меняет предел. Компьютер должен оставаться включённым, подключённым к интернету и не уходить в сон. Автозапуск после перезагрузки Windows сам не устанавливается.

Если переменные уже заданы, можно запускать Python непосредственно:

```powershell
.\.venv\Scripts\python.exe -m bridge --config config.toml check
.\.venv\Scripts\python.exe -m bridge --config config.toml run
```

`check` проверяет обязательные поля и наличие переменных **без сети**. `run` проверяет подключение, права, privacy и соответствие webhook. Успешный запуск выдаёт `Discord connected`, `Telegram connected`, `pair=1 ... configured`, `Bridge ready`. Раз в минуту выводятся количества pending/failed/uncertain. Имена людей, содержимое сообщений, ID чатов, токены и webhook URL в runtime-логи не выводятся. Номер `pair=1` соответствует первой секции `[[pairs]]` в файле.

Остановка: **Ctrl+C**. Уже принятые события остаются в SQLite. Если процесс принудительно прерван во время отправки, такая операция проверяется как спорная при следующем запуске.

## Ошибки и спорные отправки

Посмотреть локальное состояние можно и во время работы:

```powershell
.\.venv\Scripts\python.exe -m bridge status
```

Команда печатает счётчики и номера проблемных заданий, без содержимого сообщений. Для изменения очереди сначала остановите мост (и скрипт автоперезапуска).

После устранения обычной ошибки, например недостатка прав, повторите задание:

```powershell
.\.venv\Scripts\python.exe -m bridge retry 17
```

`17` — пример, используйте реальный номер из `status`.

Если состояние `uncertain`, платформа могла принять запрос до обрыва связи. Автоматического повторения по умолчанию нет. Если сообщение **найдено** в целевом чате, подтвердите его фактический ID:

```powershell
.\.venv\Scripts\python.exe -m bridge resolve 17 123456789
```

После запуска мост продолжит оставшиеся части. В Discord ID копируется через Developer Mode. В Telegram ID виден в ссылке на сообщение супергруппы (`.../<message_id>`); для обычной группы при необходимости используйте доверенный Telegram-клиент, показывающий ID. Если сообщение действительно **не появилось**, разрешите повтор вручную:

```powershell
.\.venv\Scripts\python.exe -m bridge retry 17 --allow-duplicate-risk
```

Если проверить наличие невозможно, оставьте задание в `uncertain`: остальные сообщения продолжат работать, его собственные последующие изменения будут ждать. Полной гарантии exactly-once на границе локальной SQLite и внешних API нет. Параметр `retry_uncertain=true` включает ограниченные автоматические повторы с риском дублей; для выбранного вами режима оставьте `false`.

| Симптом/код | Что проверить |
| --- | --- |
| Не заданы переменные окружения | Запустите `scripts/start.ps1` и введите секреты; не подставляйте примеры |
| Discord `LoginFailure`, Telegram `InvalidToken` | Токен соответствующего бота; при отзыве замените его в окружении |
| Discord close 4014 / `PrivilegedIntentsRequired` | Message Content Intent в Developer Portal |
| Telegram видит только команды | Group Privacy выключен; после изменения бот удалён и добавлен заново |
| `permissions`, `Forbidden`, `bad_request` | Членство бота, разрешения канала/группы, ID, доступность темы, актуальность webhook |
| Конфликт polling / `Conflict` | Другой процесс использует того же Telegram-бота либо настроен webhook |
| `discord_not_ready` | Discord переподключается; задание повторится в пределах `max_attempts` |
| `rate_limit` | Учитывается задержка API; текст + каждый файл + изменение расходуют отдельные запросы |
| `ambiguous_send` | Проверьте целевой чат и используйте `resolve` или осознанный `retry` |
| Удаление/редактирование старого сообщения не проходит | Ограничение API, отсутствующая копия или права; задание останется `failed` |
| `sqlite`/`OperationalError` | Свободное место, права на папку `data`, локальный диск, отсутствие второй копии процесса |

Программа не отключает существующий Telegram webhook сама, чтобы не нарушать другую интеграцию. Лучше создать отдельного Telegram-бота для моста. При необходимости отключения webhook сделайте это осознанно через официальный Bot API, не вставляя токен в адресную строку или логи.

## Поддерживаемые ограничения

- Discord: до 2000 символов в текстовой части; Telegram: до 4096. Разбиение учитывает UTF-16, emoji и длину уже экранированного текста.
- Общий лимит файла по умолчанию 20 MB (`max_file_mb`, настраивается до 50). Для больших файлов из Discord в Telegram можно поднять его до 50 MB; загрузка в Telegram допускает до 50 MB, но скачивание вложений из Telegram Bot API ограничено 20 MB. Discord дополнительно применяет фактический `guild.filesize_limit`, даже если он ниже настройки. Фото Telegram ограничены 10 MB и требованиями к изображению. Локальный Telegram Bot API server не используется.
- Фото Telegram могут быть сжаты самой платформой. Для сохранения исходных байтов отправляйте изображение как файл. Изображения, не распознанные платформой, могут остаться обычными файлами без предпросмотра.
- Текст и файлы отправляются отдельными сообщениями. Альбомы доставляются как отдельные элементы, не собираются заново в альбом. Если старое вложение нельзя удалить из-за ограничений API, синхронизация останется частичной, а ошибка будет видна в `status`.
- Удаление Telegram → Discord недоступно для обычных групповых сообщений. Telegram также ограничивает удаление сообщений по возрасту (обычно менее 48 часов). Нужны сохранённые ID; история, существовавшая до запуска моста, не импортируется. События удаления/редактирования Discord, пропущенные во время полного отключения, не восстанавливаются сканированием истории.
- Telegram Bot API отправляет сообщения от имени самого бота и не позволяет задать для каждого сообщения динамическое имя или аватар автора. Поэтому подпись `[Discord] Имя:` остаётся в теле сообщения Telegram, а текст начинается со следующей строки; для сообщений только с медиа используется подпись к медиа. Общий аватар и имя бота можно задать в BotFather. Стиль bold/italic и сложные platform-specific embeds/rich messages не конвертируются в полноценную разметку. Сохраняются текст, переносы, доступные ссылки и цитаты; Markdown Discord передаётся буквально в Telegram. В Telegram `parse_mode=None`, в Discord текст экранируется и все mentions запрещены. Это сохраняет читаемость без выполнения пользовательской разметки и пингов.
- Стикеры, опросы и другие неподдерживаемые пользовательские типы дают понятное уведомление. Служебные события не пересылаются. Защищённое Telegram-содержимое заменяется уведомлением.
- Discord Gateway переподключается средствами SDK. Telegram polling после 10 последовательных сетевых ошибок завершает процесс для перезапуска. Принятые в SQLite события сохраняются; Telegram подтверждается только после записи. Telegram хранит неполученные updates не более 24 часов. Discord Gateway не гарантирует долговременную очередь во время отключения. Ссылки CDN Discord могут истекать до отложенного скачивания; тогда текст сохраняется, а вместо файла приходит уведомление.
- SQLite хранит текст/авторов/ID и метаданные файлов, без самих бинарных вложений. История автоматически не очищается: она нужна для дедупликации и связей ответов. Храните `data` доступной только нужному пользователю; резервную копию всей базы делайте после остановки процесса. База и `config.toml` исключены из Git. Потеря базы означает потерю соответствий и защиты от исторических повторов.
- Это решение для небольшой группы и локального диска, без распределённого запуска, транзакции между двумя платформами или гарантии неизменного порядка разных сообщений. На постоянной нагрузке выше лимита Telegram очередь будет расти; наблюдайте `health pending` и свободное место.

## Проверки разработки

Команды для тестирования собраны в [TESTING.md](TESTING.md), а установка и обслуживание сервера — в [SERVER_COMMANDS.md](SERVER_COMMANDS.md).

```powershell
.\.venv\Scripts\python.exe -m pip install ruff build setuptools wheel
.\scripts\check.ps1
```

Используется стандартный `unittest` с моками платформ, проверяется передача в обе стороны, фильтры, дубли, SQLite/recovery, ответы, изменения, вложения, безопасное форматирование, ограничения размеров, 429/5xx, неопределённые отправки и скрытие секретов в логах. Сборка создаёт wheel и sdist в `dist`. Это **не проверка реального подключения**: для него нужны два настоящих токена, webhook URL и два ID чатов.

После настройки отдельно выполните приёмку в реальных чатах: текст в обе стороны, фото, документ, длинный текст, ответ на пересланное сообщение, редактирование, удаление Discord-оригинала и перезапуск. Проверить, что Telegram-удаление не синхронизируется, также полезно. Не используйте боевой чат для массовых тестов.
